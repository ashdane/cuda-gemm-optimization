\subsection{Measurement Methodology}

Primary timing is conducted via CUDA event pairs (\texttt{cudaEventRecord} and \texttt{cudaEventElapsedTime}) surrounding each kernel launch, capturing GPU execution time without PCIe transfer overhead. 

\begin{itemize}[nosep, leftmargin=1.4em]
\item 10 warmup runs (discarded) are executed before each timed sequence, followed by 100 timed runs per configuration.
\item Median times are reported to remain robust against contention on shared nodes.
\item SLURM is used to pin execution to a single GPU via \texttt{CUDA\_VISIBLE\_DEVICES}. 
\end{itemize}

Every kernel is validated against \texttt{cublasSgemm} for dimensions up to $256^3$. The maximum absolute error observed is $1\times10^{-2}$ for FP32 and $5\times10^{-1}$ for FP16 TC kernels. 

\paragraph{Profiler Access and Instrumentation:}
Runtime execution timelines and API overheads on the Ada cluster are empirically measured using \textbf{NVIDIA Nsight Systems (\texttt{nsys})}, producing complete execution traces (\texttt{profiling/*.nsys-rep}) and SQLite profiles for kernel latency, stream synchronization, and memory copy overheads. Because fine-grained hardware performance registers via \textbf{NVIDIA Nsight Compute (\texttt{ncu})} were blocked on the shared cluster by the non-root restriction flag \texttt{NVreg\_RestrictProfilingToAdminUsers=1} (\texttt{ERR\_NVGPUCTRPERM}), we executed root-level Nsight Compute runs on a Turing-architecture NVIDIA Tesla T4 GPU (sm\_75) with binary reports saved in \texttt{colab\_profiling/*.ncu-rep}. This provides direct, hardware-level physical counter verification (exact L1 sector counts, L1 cache hit rates, shared memory bank conflict cycles, and warp active percentages) directly confirming our analytical models.

\section{Kernel Progression}

The following sections detail the progression of kernel optimizations, their expected theoretical benefits, and actual measured performance.

\begin{description}[style=nextline, leftmargin=0pt, itemsep=0.3em, parsep=0pt]
\item[\color{accent}K0 --- Naive]
One thread per output element. Each thread loops over K, reloading \texttt{A[row,k]} and \texttt{B[k,col]} from global memory every iteration. Zero data reuse leads to severe memory bandwidth bottlenecks.

\item[\color{accent}K1 --- Coalesced]
Fixes standard mapping issues to ensure the fast-varying thread dimension maps to the fast-varying column, improving memory coalescence.

\item[\color{accent}K2 --- Shared Memory Tiling]
Utilizes a $32{\times}32$ tile of A and B in shared memory, allowing each element to be reused 32 times. This increases arithmetic intensity and reduces bank conflicts.

\item[\color{accent}K3 --- 1D Block Tiling]
Increases instruction-level parallelism (ILP) by having each thread compute 8 rows (BM=64, BN=64, BK=8), yielding 8 FMAs per shared-memory load.

\item[\color{accent}K4 --- 2D Block Tiling]
Each thread computes $8{\times}8$ outputs (256 threads/block). This optimization trades theoretical occupancy for higher ILP.

\item[\color{accent}K5 --- Vectorized]
Utilizes \texttt{float4} loads to cut instruction counts for global to shared memory transfers, yielding better bandwidth utilization.

\item[\color{accent}K6 --- Warp Tiling]
Explicit warp-level decomposition where 8 warps per block each compute a $64{\times}32$ sub-region.

\item[\color{accent}K7 --- Double Buffering]
Implements software pipelining to prefetch the next tile while FMA units consume the current one, increasing latency hiding at the cost of shared memory footprint.

\item[\color{accent}K8 --- Tensor Core WMMA (Turing sm\_75 only)]
\label{sec:k8}
Utilizes the WMMA API with \texttt{\_\_half} inputs and \texttt{float} accumulation on $16{\times}16{\times}16$ fragments. 

\item[\color{accent}K9 / K10 --- cuBLAS]
Provides the vendor-tuned ceilings for FP16 and FP32 respectively, establishing an upper performance bound.

\end{description}

Performance scales more effectively on Turing across heavily interleaved instruction streams. Microarchitecturally, this divergence stems from the fundamental pipeline reorganization between Pascal and Turing:
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Pascal (sm\_61) Shared Datapaths}: The Pascal SM features unified execution datapaths where integer arithmetic and floating-point operations contend for the same dispatch ports. Address generation math (e.g., computing multi-dimensional matrix strides $row \cdot K + col$ and pointer offsets via \texttt{IMAD}/\texttt{LEA}) cannot issue concurrently with floating-point multiply-accumulate (\texttt{FFMA}) instructions. The warp scheduler must sequentially alternate between address calculation and arithmetic, stalling the FP32 pipeline.
  \item \textbf{Turing (sm\_75) Independent Concurrent Pipelines}: In the Turing microarchitecture, each SM sub-core integrates dedicated, independent INT32 and FP32 execution datapaths. Turing can dual-issue and execute an integer address instruction and a floating-point \texttt{FFMA} in the exact same clock cycle. In deeply unrolled GEMM kernels (K4--K7), compiler-generated address index increments and pointer arithmetic are executed entirely in parallel with the math pipeline, effectively eliminating loop overhead and achieving an empirical 1.4--1.7$\times$ throughput gain over Pascal.
\end{itemize}

\subsection{Parameter Sensitivity Analysis}

To systematically investigate microarchitectural performance cliffs, we executed an exhaustive empirical sweep across the block-tile ($BM, BN$), K-depth ($BK$), and thread-tile ($TM, TN$) hyperparameter grid on the Turing RTX 2080 Ti ($M=N=K=4096$, 50 iterations per point, recorded in \texttt{results/param\_sweep\_NVIDIA\_GeForce\_RTX\_2080\_Ti\_20260907\_153954.csv}).

\begin{itemize}[leftmargin=1.5em]
  \item \textbf{The $TN$ Bank Conflict Cliff}: Across all tile configurations with $BK=16$, doubling thread tile width from $TN=4$ to $TN=8$ precipitates a sharp, non-linear performance collapse. For example:
  \begin{itemize}
    \item At $BM=64, BN=128, BK=16$: Configuration $TM=4, TN=4$ achieves \textbf{7560.0 GFLOPS} ($100\%$ occupancy). Shifting to $TM=4, TN=8$ plunges throughput to \textbf{4719.1 GFLOPS}---a \textbf{37.6\% performance collapse}.
    \item At $BM=64, BN=64, BK=16$: Moving from $TN=4$ (7286.8 GFLOPS) to $TN=8$ (3607.0 GFLOPS) causes an immediate \textbf{50.5\% collapse}.
  \end{itemize}
  This empirical cliff directly validates our shared memory bank conflict derivation: 8-wide contiguous vector loads within 128-byte shared memory rows map adjacent threads $t$ and $t+4$ to identical memory banks ($8t \equiv 8(t+4) \pmod{32}$), halving effective shared memory load bandwidth through 2-way serialization replays.
  \item \textbf{Optimal Empirical Operating Point}: Maximum sustained single-precision throughput is reached at $BM=128, BN=128, BK=32$ with $TM=8, TN=4$, attaining \textbf{8084.9 GFLOPS} ($60.1\%$ of peak) with 256 threads per block ($50\%$ occupancy). This configuration balances high instruction-level parallelism (64 FMAs per thread iteration) with conflict-free 4-wide register loads.
  \item \textbf{Thread Granularity vs.\ Occupancy}: Interestingly, $100\%$ theoretical occupancy does not correlate with peak throughput. Configurations with $12.5\%$ occupancy ($BM=32, BN=32, TM=8, TN=4$) sustain 5601.2 GFLOPS by saturating arithmetic pipelines through high per-thread ILP, proving that GEMM kernels on modern architectures are bounded by instruction scheduling and bank contention rather than thread-level parallelism (TLP).
\end{itemize}

\subsection{Empirical Timeline and API Profiling (Nsight Systems)}
\label{sec:nsys}

\subsection{First-Principles Microarchitectural Modeling: Coalescing and Bank Conflicts}

\textbf{\textit{Methodological Note: Because fine-grained hardware PMCs (via \texttt{ncu}) were restricted on the cluster by the \texttt{ERR\_NVGPUCTRPERM} driver flag, the coalescing efficiencies and bank-conflict degrees below are derived from first-principles spatial address analysis of kernel access strides, and then validated empirically against our measured parameter sweeps.}}

The efficiency of global memory load transactions is governed by the spatial alignment of memory requests within each 32-thread warp:
\begin{equation}
\text{Coalescing Efficiency} = \frac{\text{Requested Bytes}}{\text{Executed DRAM Transaction Bytes}} \times 100\%
\end{equation}

\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Naive Kernel (K0)}: Threads map $col = threadIdx.y$ and $row = threadIdx.x$. Within warp 0 ($threadIdx.y=0$, $threadIdx.x \in [0, 31]$), consecutive threads access matrix $B[k \cdot N + col]$ with a row-major memory stride of $N$. For $N=4096$, each 4-byte float requested by thread $i$ lies at offset $i \times 4096 \times 4 = i \times 16{,}384$ bytes. Because every access misses adjacent 32-byte memory sectors, the memory controller must issue \textbf{32 individual 32-byte DRAM sector transactions} (1024 bytes transferred) to satisfy a single 128-byte warp request:
  \begin{equation}
  \text{Efficiency}_{\text{K0}} = \frac{32 \times 4\text{ B}}{32 \times 32\text{ B}} = \frac{128\text{ B}}{1024\text{ B}} = \mathbf{12.5\%}
  \end{equation}
  This causes severe memory bus saturation and explains the poor 581.5 GFLOPS throughput.
  \item \textbf{Coalesced Kernel (K1)}: Swapping the thread mapping so $col = threadIdx.x$ ensures that threads $0 \dots 31$ in the warp request elements $B[k \cdot N + 0], \dots, B[k \cdot N + 31]$. These 32 consecutive single-precision floats span exactly 128 contiguous bytes, perfectly coalescing into four 32-byte sectors (one 128-byte cache line transfer):
  \begin{equation}
  \text{Efficiency}_{\text{K1}} = \frac{128\text{ B}}{128\text{ B}} = \mathbf{100.0\%}
  \end{equation}
\end{itemize}

\subsection{Shared Memory Bank Conflict Quantification}

Both Pascal and Turing shared memory systems are organized into 32 banks, where each bank has a 4-byte (32-bit) word width. The physical bank address is determined by:
\begin{equation}
\text{Bank ID} = \left( \frac{\text{Byte Address}}{4} \right) \pmod{32}
\end{equation}
If two or more threads within the same warp request distinct addresses mapping to the same Bank ID, the requests are serialized into multiple memory clock cycles (an $m$-way conflict causes an $m$-cycle replay penalty).
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Kernel 2 (Smem Tiling)}: During matrix multiplication from tiles, threads read:
  \begin{itemize}
    \item $tileB[k][threadIdx.x]$: Thread $t$ accesses index $k \cdot 32 + t$. Since Bank ID $= (k \cdot 32 + t) \pmod{32} = t$, each thread $t \in [0, 31]$ maps to an independent bank ($0 \dots 31$), yielding \textbf{0 bank conflicts (1-way conflict-free)}.
    \item $tileA[threadIdx.y][k]$: All 32 threads in the warp share the exact same $threadIdx.y$, thus requesting the exact same memory word. The hardware shared memory broadcast unit detects this address equality and distributes the word to all 32 lanes in a single cycle ($\mathbf{0\text{ bank conflicts}}$ via broadcast).
  \end{itemize}
  \item \textbf{Kernel 4 (2D Block Tiling)}: Threads load register vectors via $Bs[dotIdx \cdot BN + threadCol \cdot TN + j]$ where $TN=8$ and $BN=128$. For a fixed $dotIdx$ and element $j$, thread $t$ accesses bank $(t \cdot 8 + j) \pmod{32}$. Because $8 \times 4 = 32$, threads $t$ and $t+4$ collide on the exact same bank:
  \begin{equation}
  (8(t+4) + j) \pmod{32} \equiv (8t + 32 + j) \pmod{32} = (8t + j) \pmod{32}
  \end{equation}
  This generates a \textbf{2-way bank conflict} across all threads in the warp, degrading raw shared memory load bandwidth by $50\%$ on every inner-loop iteration unless memory padding is introduced.
\end{itemize}

\section{Discussion}

\subsection{Alternative Processing Paths}

While cuBLAS serves as the baseline target, the tensor core optimization path diverges significantly. The manual WMMA approach achieved 6.7 TFLOPS (roughly 6.3\% of the true TC peak) due to fragment loads fetching directly from global memory. By staging intermediate fragment data through shared memory to sustain throughput, the cuBLAS FP16 implementation scales efficiently up to 34.2 TFLOPS.
